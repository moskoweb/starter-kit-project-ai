# Phase 02 — Research

Pesquisa: 2026-11-11. Escopo: AUTH-01–03, TEN-01–06, MAIL-01. Pesquisa documental e registry; não representa integração executada.

## APIs e versões verificadas

Registry npm consultado: `better-auth`, `@better-auth/drizzle-adapter` e CLI `auth` em **1.7.20**; `nodemailer` **10.5.0**, `resend` **6.38.0**. `@better-auth/cli` antigo retorna 1.4.21: não usar. `better-auth` não possui bin; bin atual pertence a `auth`. Pin exato e lockfile canônico; revisar changelog antes de instalar. Drizzle e postgres.js existentes permanecem.

Fontes primárias:
- [Drizzle adapter](https://better-auth.com/docs/adapters/drizzle.md): `drizzleAdapter` de `@better-auth/drizzle-adapter`, `provider: "pg"`, `schema`; geração Better Auth seguida por migration Drizzle. Não usar `auth migrate` com Drizzle.
- [Database e UUID](https://better-auth.com/docs/concepts/database.md): `advanced.database.generateId: "uuid"` gera schema UUID e, em PostgreSQL, permite UUID pelo banco; `defaultRandom()` usa `gen_random_uuid()` (UUIDv4 em PostgreSQL17). `crypto.randomUUID()` é alternativa nativa, mas callback customizado não informa tipo UUID ao gerador; preferir opção nativa `"uuid"`.
- [Next.js](https://better-auth.com/docs/integrations/next): `export const { GET, POST } = toNextJsHandler(auth)`; `getSession({ headers })` no servidor. Cookie existente não prova sessão. `nextCookies()` somente se usar Server Actions e por último nos plugins; formulários podem usar client HTTP nativo sem este plugin.
- [Email/password](https://better-auth.com/docs/authentication/email-password.md): `signUp.email`, `signIn.email`, `signOut`, `requestPasswordReset`, `resetPassword`; server equivalentes `signUpEmail`, `signInEmail`, `requestPasswordReset`, `resetPassword`. Configurar `requireEmailVerification: true`, `revokeSessionsOnPasswordReset: true`.
- [Email](https://better-auth.com/docs/concepts/email.md): `emailVerification.sendVerificationEmail({ user, url, token })`, `sendOnSignUp: true`, `sendVerificationEmail` no client; não logar url/token. Reset usa `emailAndPassword.sendResetPassword({ user, url, token })`. Usar origem/callbacks locais permitidos, sem open redirect.
- [Organization](https://better-auth.com/docs/plugins/organization.md): `organization({ ac, roles, sendInvitationEmail(data), requireEmailVerificationOnInvitation: true })`; client `organization.create`, `inviteMember`, `acceptInvitation`, `rejectInvitation`, `cancelInvitation`, `listMembers`, `removeMember`, `updateMemberRole`, `setActive`; server `createOrganization`, `createInvitation`, `acceptInvitation`, `removeMember`, `updateMemberRole`, `hasPermission`. Convite requer sessão com email correspondente. `data.id`, `data.email`, `data.organization`, `data.inviter` vêm do callback (não presumir objeto `invitation`).
- [Access control](https://better-auth.com/docs/plugins/organization.md#custom-permissions): `createAccessControl` de `better-auth/plugins/access`; compor `defaultStatements`, `ownerAc`, `adminAc`, `memberAc` de `better-auth/plugins/organization/access` com ações de `project`. Preservar permissões nativas de organização/member/invitation; não inventar `member.invite`. Passar **ac e roles** tanto ao plugin server quanto `organizationClient`. Roles estáticas customizadas em código, `dynamicAccessControl` e teams desativados.
- [Admin](https://better-auth.com/docs/plugins/admin.md): `admin({ defaultRole: "user", adminRoles: ["admin"] })` (não `adminRole`). `user.role` separado de `member.role`. Campos de autoridade têm `input:false`; payload malicioso pode ser rejeitado, não afirmar descarte silencioso. Aceite: nunca persiste privilégio. Superadmin não recebe bypass RLS, impersonação não requerida; limitar permissões globais ao necessário.
- [Two-factor](https://better-auth.com/docs/plugins/2fa.md): `twoFactor`, `twoFactorClient`; `enable({ password, method: "totp" })` retorna `totpURI`/`backupCodes`; `verifyTotp` confirma enrollment, sem `skipVerificationOnEnable`. `sendOtp`/`verifyOtp`, `generateBackupCodes`/`verifyBackupCode`, `disable`. Server: `enableTwoFactor`, `verifyTOTP`, `sendTwoFactorOTP`, `verifyTwoFactorOTP`, `generateBackupCodes`, `verifyBackupCode`, `disableTwoFactor`. `twoFactorRedirect` significa desafio, não sessão autenticada. `otpOptions.sendOTP({user,otp})`, `period` em minutos, `allowedAttempts`, `storeOTP:"hashed"`; lockout nativo habilitado. TOTP aceita janela ±1 período: provar replay no mesmo desafio/novo desafio; não prometer anti-replay entre desafios sem verificar implementação pinada. Se replay passar, corrigir atomicamente último timestep por usuário (mínima extensão, não criptografia própria) antes de concluir AUTH-02.
- [Resend send](https://resend.com/docs/api-reference/emails/send-email): `new Resend(key).emails.send({from,to,subject,html,text})` retorna `{data,error}`; checar `error` mesmo sem throw.
- [Nodemailer SMTP](https://nodemailer.com/smtp): `nodemailer.createTransport` (não `createTransporter`), `sendMail`; TLS/STARTTLS conforme config, nunca desabilitar TLS globalmente. Mailpit local permite `secure:false` sem auth; provedor externo exige configuração explícita.
- [PostgreSQL17 RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [SET LOCAL](https://www.postgresql.org/docs/17/sql-set.html), [set_config](https://www.postgresql.org/docs/17/functions-admin.html): owner/BYPASSRLS contornam políticas; runtime deve ser role DML não owner/NOBYPASSRLS. `set_config(name,value,true)` só é seguro dentro da mesma transação/conexão.

## Schema e fundação real

Fundação atualmente expõe `getDb()`, `getSql()`, `closeDb()` em `packages/db/src/client.ts`; `schema.ts` é agregador e contém `appSettings`. Não planejar singleton `db` inexistente nem substituir schema por diretório removendo export atual. Adicionar `auth-schema.ts`, `domain-schema.ts`, reexportados por `schema.ts`, preservando `appSettings`. CLI/script usa client standalone; barrel server contém `server-only`. Evitar ciclo db → auth → db: db não importa auth; autorização e domínio na aplicação/auth consomem db.

Schema Better Auth deve ser gerado por **`auth@1.7.20 generate`**, carregando configuração completa dos plugins e `generateId:"uuid"`; obter flags exatas com `--help` na execução. Não colar schema manual deste documento. Gerador usa [getAuthTables](https://github.com/better-auth/better-auth/blob/main/packages/cli/src/generators/drizzle.ts); comparar saída contra `getAuthTables(auth.options)` da versão instalada e metadata do banco. Fontes `main` são alerta de drift, não contrato da versão pinada. Checklist não exaustivo: admin `session.impersonatedBy`; two-factor `verified`, `failedVerificationCount`, `lockedUntil`; organization `invitation.createdAt`, demais campos gerados. Conferir índices, uniqueness membership `(organizationId,userId)`, slug único e FKs; preservar nomes de modelos esperados pelo adapter. Nenhuma migration histórica editada.

## RLS executável e limites de segurança

- Better Auth core e plugins **sem RLS** nesta estratégia: login/sessão/convites usam API nativa com checks do plugin, sem tenant prévio. Isso é escolha de integração, não impossibilidade técnica universal. Não expor CRUD genérico dessas tabelas. `app_settings` não é dado pessoal/tenant.
- `projects` é domínio real continuado na fase4, não fixture descartável: `id uuid`, `organizationId uuid nullable`, `ownerUserId uuid not null`, `name`, `description`, timestamps. Relação `tasks` (`id`, `projectId`, `organizationId`, `ownerUserId`, `title`) prova relações agora e será reutilizada. Escopos idênticos na relação validados no servidor e constraint/trigger de banco, inclusive NULL pessoal; FK somente por projectId não prova isolamento.
- API recebe rota/body não confiável; `requireSession(headers)` consulta sessão atual (sem cache de cookie para autoridade); resolve UUIDv4/slug; verifica membership/role **no banco a cada operação** e permissão conforme ação. `activeOrganizationId` é preferência de UI, nunca autoridade; não trocar contexto global compartilhado entre requisições.
- Resolver abre transação, relê/valida membership e mantém lock compatível com remoção (`FOR SHARE`) até commit para linearizar revogação: operação iniciada antes da remoção pode terminar; após remoção confirmada, novas operações negadas. Alteração de role deve respeitar mesmo lock. Contexto é derivado no servidor, helper interno não aceita userId/tenantId livre do cliente.
- Dentro dessa transação, sempre setar ambos GUCs (`app.current_user_id` e `app.current_tenant_id`), tenant `''` para pessoal. Callback usa **somente tx**, nunca `getDb()` externo. Commit/rollback descarta valores; sem SET de sessão, sem Promise paralela no mesmo tx. Pool existente max5 preservado. PgBouncer transaction pooling possível apenas com transação; não afirmar testado.
- Policies `TO vibe_starter_app`, `ENABLE` e `FORCE ROW LEVEL SECURITY`; `USING`/`WITH CHECK` fail-closed. Converter via `NULLIF(current_setting(...,true),'')::uuid`, nunca depender de short-circuit antes de cast vazio. Org: tenant não nulo, linha.organizationId igual tenant e user autenticado não nulo. Pessoal: tenant nulo, linha.organizationId nula e owner igual user. INSERT/WITH CHECK exige owner igual user; UPDATE não pode mover owner/org (colunas imutáveis por trigger ou GRANT UPDATE só das colunas editáveis). Sem política implícita de bypass global. SQL direto com GUC arbitrário pode falsificar identidade: RLS protege omissões de filtro no app confiável, **não** comprometimento da role SQL/app. Documentar fronteira, testar sem GUC/tenant errado, não prometer segurança contra SQL arbitrário com credencial runtime.

## Email, UI e gates

Funções `sendMail(message)` selecionam uma função SMTP ou Resend; sem classes/factory/retry/fallback. Contrato `{to,subject,text,html} → Promise<{id:string}>`; renderer escapa nomes e URLs e não inclui senha. `EMAIL_PROVIDER` enum, `EMAIL_FROM`, SMTP host/port/secure/auth ou RESEND_API_KEY validados só quando selecionados. Não hardcode .local em produção. Falha lança código sanitizado `EMAIL_SEND_FAILED`, com provider/código seguro no log; sem endereço, body, token, URL, chave ou mensagem bruta de provedor. Resposta ao usuário acionável sem detalhes internos. Await do callback permite falha visível; documentar tradeoff de timing de enumeração e manter resposta genérica de conta inexistente com rate limit nativo. Não background fire-and-forget silencioso.

Mailpit autorizado: SMTP127.0.0.1:11025, UI/API18025, v1.27.4. Captura local prova SMTP real, não entrega externa. Resend adapter real aguarda key/remetente/destinatário autorizado para verificação externa; solicitar só nesse gate, não bloquear trabalho local nem declarar MAIL-01 integral antes disso.

UI funcional simples com forms HTML/React e labels/erros/foco/loading: cadastro/login/logout, reenvio/consumo verificação, forgot/reset, desafio OTP/TOTP/backup, enrollment e recovery/security, criar/listar organizações, convidar/aceitar/rejeitar/cancelar, listar/remover membros/trocar roles. Sem antecipar design system/painéis fase3. TOTP URI apresentado localmente (texto copiável e QR local se adotado); nunca serviço QR externo. Backup codes exibidos uma vez, botão copiar/download local, regeneração invalida antigos; perda de todos fatores exige procedimento explícito, não bypass por reset de senha.

Rotas tenant usam config server `{prefix, identifier:"slug"|"uuid"}` por painel futuro; centralizar builder/resolver, validar prefixo/segmentos/reservados. Route Group Next não cria prefixo; usar catch-all com resolver configurado ou rewrite validado, sem impor `/org` irreversível. Slugs normalizados, únicos, proibir UUID-like e reservados para evitar ambiguidade. Perfis `personal|organizations|hybrid`, `single|multi`: personal não monta endpoints organization; single exige ID configurado de organização existente, criação pública desativada; hybrid referência multi. Mesmas verificações servidor em todos.

Owner executa provas após todas edições; nenhum build/teste executado por este planejamento. Matriz detalhada no PLAN. Maior risco: replay/concurrency reais dos fatores na versão pinada; gates bloqueantes, não assumir por documentação.
