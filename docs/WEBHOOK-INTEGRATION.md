# Webhook integration

Inbound endpoint: `POST /api/webhooks/inbound/<endpointId>`. Configure one endpoint with `WEBHOOK_INBOUND_ENDPOINT_ID`, `WEBHOOK_INBOUND_SECRET`, `WEBHOOK_INBOUND_OWNER_USER_ID`, and optional `WEBHOOK_INBOUND_OWNER_ORGANIZATION_ID`. The endpoint remains unavailable (404) until all required endpoint/owner values are valid. Configure the owner using trusted deployment values; never accept tenant or recipient identity from the request body.

Request limit is 256 KiB, checked while reading raw bytes before JSON parsing. Signature headers: `x-webhook-timestamp` and `x-webhook-signature: sha256=<hex>`; timestamps allow five minutes. Accept only signed `project.create.requested` envelopes with UUID `id` and strict `data: { name, description? }`. The configured owner comes only from environment; authorization checks active user and organization create membership. Receipt, new project, and `project.created` outbox event commit atomically. Identical replay returns 200; same ID with different raw body returns 409.

Outbound delivery uses deployment configuration, not persisted secrets: `WEBHOOK_OUTBOUND_URL`, `WEBHOOK_OUTBOUND_SECRET`, and comma-separated `WEBHOOK_OUTBOUND_ALLOWED_HOSTS`. HTTPS, exact host allowlist, public DNS, and pinned DNS required. `createDelivery(tx, context, eventId, payload)` persists pending delivery in caller transaction. `relayWebhookDeliveries(boss)` sends due records transactionally through pg-boss and marks them queued; owner calls it in relay loop and registers `webhookHandler`. Handler is idempotent for terminal statuses. Retry delay doubles from 30 seconds, caps at 24 hours, and stops after five attempts. `listDeliveries` and `retryDelivery` require authorized tenant transaction.

DB schema is declared in `packages/db/src/webhook-schema.ts`; migration generation/application and worker registration are explicit deployment-owner operations. Secrets are environment references and never stored in DB.
